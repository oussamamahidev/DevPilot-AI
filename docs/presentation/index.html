01 · Context

LLMs are rewriting software engineering

⚙️

A new interface to knowledge

LLMs let any employee query documentation, code and process knowledge in natural language — no SQL, no search syntax.

🏢

Why companies build internal AI

Public models can't see private repos, runbooks or specs — and sending that data outside is a compliance risk. The value is internal, grounded AI.

⚠️

Where generic chatbots break

They answer confidently from parametric memory — no sources, no audit trail, no way to know why an answer was produced.

A demo chatbot answers a question. A production AI system has to prove the answer is correct — and let an engineer debug it when it isn't.

🎯 KEY MESSAGE: The interesting problem in 2026 is not "can an LLM answer?" — it's "can you operate it safely at enterprise scale?"

🎤 SAY: "LLMs gave us a magical interface to knowledge. But the moment a company puts one in front of real users on real internal data, three questions appear that a demo never asks: where did this answer come from, is it actually correct, and who can I show when it's wrong? Generic chatbots have no answer to any of those."

❓ Q: Isn't this just RAG, which is well known?
A: RAG solves grounding. It does not solve operations — observability, evaluation, traceability, governance. That operational layer is the actual contribution.

01 · Problem

Six gaps between a chatbot and a trustworthy system

Knowledge is fragmented. Specs, wikis, PDFs and runbooks live in silos — no single grounded source of truth.

Documentation is hard to exploit. Long, unstructured documents are not directly usable by an LLM.

LLMs hallucinate. Plausible, fluent, and wrong — with no built-in signal that anything is off.

Answers aren't traceable. No citations, no record of which sources or steps produced the output.

No observability. When quality drops, teams are blind — no metrics on retrieval or faithfulness.

No governance. No roles, no isolation between tenants, no audit log of who asked what.

Problem statement: How do we deliver answers that are grounded, measurable, traceable and governed — not just fluent?

🎯 KEY MESSAGE: Six concrete, defensible gaps — each one maps to a feature later in the deck.

🎤 SAY: "I framed the problem as six gaps. Notice they aren't all AI problems — three of them are operations and governance problems. That framing is what shaped the whole architecture: every gap on this slide has a corresponding subsystem in DevPilot."

❓ Q: Which gap is hardest?
A: Hallucination, because you can't fully eliminate it — so my answer is to measure it (faithfulness + hallucination score per answer) and correct it (corrector agent), rather than pretend it's solved.

🎯 KEY MESSAGE: A real, tuned pipeline — every stage has concrete, defensible parameters.

🎤 SAY: "The top row is the ingestion path, the bottom row is the query path. The numbers are real and tuned: 800-token chunks with 150 overlap, 15 candidates retrieved, reranked down to the 5 best, context capped at 6,000 characters. And critically — the system enforces citations; if the model produces an answer without one, a guard injects the source."

❓ Q: Why 800/150 chunking?
A: Large enough to preserve a coherent idea, small enough that the top-5 fit the context budget; 150 overlap (~19%) prevents losing facts that straddle a boundary. Tuned empirically.

❓ Q: What is RRF?
A: Reciprocal Rank Fusion — merges semantic and keyword rankings by summing 1/(k+rank). It's robust because it needs no score calibration between the two systems.

❓ Q: What does the reranker use?
A: Default is a heuristic (keyword overlap, exact-term match, original score, rank prior); an optional LLM reranker can be enabled. I'll detail this on the agents slide.

04 · Ingestion

Asynchronous ingestion pipeline

  1. Upload → POST /workspaces/{id}/upload; file stored, row created with status uploaded, task enqueued.
  2. Celery picks it up from Redis — the API stays non-blocking and returns instantly.
  3. Extract → clean → chunk (800/150) → token count per chunk.
  4. Embed in batches of 4 via Ollama nomic-embed-text (768-d).
  5. Upsert to Qdrant (devpilot_chunks, cosine) and persist chunk rows; status → indexed.

Every transition is observable in the RAGOps pipeline view; failed docs can be re-queued from the dashboard.

🎯 KEY MESSAGE: Ingestion is async, fault-tolerant and fully observable — not a blocking upload handler.

🎤 SAY: "Ingestion was an early engineering decision. Embedding a large PDF takes seconds to minutes, so I never do it in the request. The upload endpoint just stores the file and drops a task on Redis; Celery workers do the heavy lifting. The document moves through an explicit status machine — uploaded, processing, indexed, or failed — and every state is visible in RAGOps, with one-click retry for failures."

❓ Q: What happens if a worker crashes mid-document?
A: The doc stays in 'processing'/'failed'; it's idempotent on re-run (chunks keyed by document_id+chunk_index, unique constraint), and RAGOps exposes a retry that re-queues it.

❓ Q: Why batch size 4 for embeddings?
A: Throughput vs. local GPU memory on Ollama — 4 saturated the model without OOM in my environment; it's configurable.

04 · Agentic RAG

Question answering — a 7-agent workflow

1 · Router — classifies the question (factual / summary / comparison / technical) and picks the retrieval strategy.

2 · Query Rewriter — normalizes short or vague queries into full questions for better recall.

3 · Retrieval — semantic / keyword / hybrid (RRF) search → 15 candidates, with a Postgres fallback.

4 · Reranker — heuristic or LLM scoring → keeps the top 5 most relevant chunks.

5 · Generator — builds the grounded prompt, calls the LLM, enforces citations.

6 · Evaluator — scores faithfulness, relevance, context precision, hallucination.

7 · Corrector — applies policy: if scores fail or context is missing, it withholds or replaces the answer instead of hallucinating ("I could not find this information…").

The corrector is the safety valve: the system would rather say "I don't know" than fabricate — and it records why.

🎯 KEY MESSAGE: Answering is a pipeline of specialized agents, each one logged — and the last two are about trust, not fluency.

🎤 SAY: "A naive RAG does retrieve-then-generate. Mine runs seven agents. The first five improve the answer; the last two protect it. The evaluator scores every answer on four axes, and the corrector enforces a policy — if faithfulness is too low or there's no supporting context, it refuses rather than inventing. Each agent's input, output and latency is persisted as an AgentRun, which is exactly what makes the whole thing traceable later."

❓ Q: Aren't 7 agents slow?
A: Router/rewriter/reranker/corrector are lightweight (heuristics or short LLM calls); only retrieval, generation and the optional LLM-evaluation are heavy. The agentic structure costs latency but buys explainability and a measurable quality floor.

❓ Q: Is the evaluator reliable (LLM judging LLM)?
A: It's a signal, not ground truth. I combine an LLM judge with deterministic heuristics (overlap, exact-match, length) so there's always a non-circular baseline; I treat scores as monitoring, not certification.

04 · Streaming

Real-time streaming over SSE

A single /chat/stream endpoint streams the whole pipeline — not just tokens — as Server-Sent Events.

// event stream the client consumes
event: start # conversation + strategy
event: trace # router → retrieval → rerank …
event: token # answer streams in live
event: citations # grounded sources
event: evaluation # faithfulness, hallucination…
event: correction # if policy triggered
event: complete # message_id → trace

Why it matters

Perceived latency ↓ — first token in ~1s vs. waiting for the full answer.

Transparency — the user watches the pipeline reason in real time.

Cancellable — client disconnect aborts work & rolls back the transaction.

Powers the Studio — the same stream drives the AI Execution Studio (slide 19).

Custom SSE parser on the client; automatic fallback to a non-streaming request if the stream fails before the first event.

🎯 KEY MESSAGE: The stream carries the whole pipeline's reasoning, not just text — and it's the backbone of the flagship feature.

🎤 SAY: "Most chatbots stream tokens. Mine streams the entire pipeline as structured events: when each agent starts and finishes, the tokens, the citations, the evaluation scores. That's a deliberate design choice — because this same event stream is what powers the live visualization I'll show you in a few slides. And it's cancellable: if the user closes the tab, the backend detects the disconnect and rolls back."

❓ Q: Why SSE and not WebSockets?
A: The flow is one-directional server→client; SSE is simpler, works over plain HTTP, auto-reconnects, and needs no extra protocol. WebSockets would be over-engineering here.

❓ Q: Doesn't storing every trace explode the DB?
A: Trace rows are small and bounded per message; JSONB keeps agent payloads compact. For scale you'd add retention/archival — the schema already isolates trace tables so they can be partitioned or rolled off independently.

❓ Q: Why keep vectors in Qdrant but metadata in Postgres?
A: Chunk text/metadata is relational and transactional (Postgres); the embedding is an ANN-search concern (Qdrant). The Chunk row links them via vector_id.

05 · Backend

Backend architecture

FastAPI — the gateway

Async REST + SSE. Routers grouped by domain: auth · documents · chat · retrieval · workspaces · admin · ragops · rag-traces · system · health. Request-ID correlation + Prometheus on every call.

Celery — the workers

Off-request ingestion: extract, chunk, embed, index. Decouples slow AI work from the API; horizontally scalable by adding workers.

Redis — broker & cache

Message broker + result backend for Celery; low-latency coordination between API and worker tiers.

Qdrant — vector engine

HNSW + cosine over the devpilot_chunks collection; payload-filtered by workspace for tenant isolation.

Ollama — local inference

Generation (qwen3:8b) + embeddings (nomic-embed-text) run on-prem. Behind a provider interface, so Gemini / OpenAI drop in without touching the orchestration layer.

🎯 KEY MESSAGE: Clean separation: a thin async gateway, a scalable worker tier, and a provider-abstracted inference layer.

🎤 SAY: "The backend is three tiers. FastAPI is a thin async gateway with domain-grouped routers and metrics on every endpoint. Celery is the muscle — all the slow embedding work. Redis brokers between them. Qdrant serves vectors, isolated per workspace. And Ollama runs the models locally behind a provider interface, which is the seam that lets me swap to a cloud model for benchmarking without changing a line of orchestration code."

❓ Q: How do you scale this?
A: API tier scales horizontally (stateless + JWT); worker tier scales by adding Celery workers; Qdrant and Postgres scale independently. The bottleneck is GPU inference, addressed by the Ollama abstraction (route to a bigger pool or cloud).

07 · Rigor · Security

Security & governance

🔑

Authentication

JWT (HS256), bcrypt-hashed passwords, 30-min expiry, OAuth2 password flow. Deactivated/deleted users can't authenticate.

🧱

Workspace isolation

Every query is scoped by workspace_id at the service layer and in Qdrant payload filters. One tenant can never read another's data.

👤

Role-based access

user / admin / super_admin (DB-enforced) + per-workspace roles. RAGOps, traces, user mgmt are admin-only; full chunk content is super-admin-only.

Audit trail: sensitive actions (admin login, deletions) are written to an audit_logs table with actor, action, target, IP and user-agent — governance isn't a slogan, it's a table.

🎯 KEY MESSAGE: Multi-tenant security is enforced in depth — at the app layer, the vector store, and the audit log.

🎤 SAY: "Governance was an objective, so it's real. Auth is JWT with bcrypt and short-lived tokens. Isolation is defense-in-depth: workspace scoping is enforced both in the service layer and as a payload filter inside Qdrant, so cross-tenant leakage isn't even possible at the vector level. Roles gate the admin tooling, and the most sensitive thing — full source content — is restricted to super-admins. And every sensitive action lands in an audit table with the actor and their IP."

❓ Q: HS256 — why not RS256?
A: Single-issuer, single-verifier service, so symmetric HS256 is sufficient and simpler. RS256 matters when multiple services verify tokens they don't issue — a clean upgrade path if the platform splits into services.

❓ Q: Token refresh / revocation?
A: Short 30-min expiry limits exposure; deactivated users are rejected at auth. A refresh-token rotation flow is a documented next step.

08 · Reflection

Challenges & key decisions

Hallucination vs. helpfulness

Tension: refuse too often and it's useless; refuse too rarely and it lies. Decision: measure (evaluator) + policy (corrector) instead of a hard rule.

Sync upload vs. async ingestion

Tension: simple blocking upload vs. complexity of a worker tier. Decision: Celery — non-negotiable for real document sizes.

Local vs. cloud models

Tension: Ollama quality/latency vs. cloud convenience. Decision: provider abstraction — local by default, cloud for benchmarking.

Streaming the whole pipeline

Tension: stream just tokens (easy) vs. stream structured trace events (hard). Decision: the harder path — it unlocked the Studio.

Lesson learned: the hard part of production AI is not the model call — it's everything around it: ingestion, evaluation, isolation, observability.

🎯 KEY MESSAGE: Show engineering maturity — name real tradeoffs and justify the calls.

🎤 SAY: "Every interesting decision was a tradeoff. The toughest was hallucination versus helpfulness — and I chose not to solve it with a brittle rule but to measure it and apply a policy. The streaming decision is a good example of investing in the harder path: streaming structured trace events instead of just tokens was significantly more work, but it's what made the Execution Studio possible. The overarching lesson: the model call is the easy 10%; the production-grade 90% is everything around it."

❓ Q: If you started over, what would you change?
A: I'd introduce evaluation datasets earlier to measure agentic-vs-linear RAG quantitatively from day one, and I'd add retention/partitioning to the trace tables sooner.
